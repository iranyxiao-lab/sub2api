# 应用分阶段发布

默认启动行为不变。候选进程配置 `SUB2API_BACKGROUND_ACTIVATION_FILE` 为容器内绝对路径，在该普通文件出现前推迟周期性清理、探测、报表、备份、监控、令牌自动刷新、定时测试及插件启动。智力测试队列执行器仍可运行，依靠数据库租约和全局领取锁限制执行。

该配置存在时始终跳过跨进程并发槽位启动清理。候选使用独立的数据目录副本；账务写入、鉴权订阅、缓存、日志、请求工作队列及提示词安全检查继续服务请求。周期任务仅激活一次，移除标记不会暂停已启动任务；回滚必须先停止候选周期任务所属实例，再恢复旧实例。

链上运行时目前不支持延迟初始化：配置链上功能的进程会拒绝分阶段模式，不能绕过此检查。插件依赖账号需在切换前单独验证；有活动插件而未验证时不切换。

## 发布顺序

1. 记录现有镜像、Compose/代理配置校验和、依赖就绪状态及其他业务容器基线。创建权限 600 的数据库与配置备份，验证备份可由 `pg_restore --list` 读取。
2. 本地构建并上传不可变镜像。候选绑定空闲 loopback 端口、独立数据副本，使用服务器现有凭据，激活标记必须不存在。不得输出环境变量或展开 Compose。
3. 检查候选的数据库迁移、依赖与鉴权 API，日志应显示周期任务 deferred。迁移失败或业务功能不可用时，不修改上游。
4. 仅修改目标应用的代理 upstream，先语法检查再平滑 reload。旧进程保持运行，等待旧代理工作进程和业务连接排空，不用固定短超时强杀。
5. 排空后停止旧应用，创建候选激活标记，确认周期任务 activated。将候选配置纳入持久化 Compose，启用重启策略，保留旧镜像和回滚配置。
6. 至少观察 10 分钟的健康、依赖、错误率、响应延迟、重启次数及其他业务状态。异常时停止发布并回滚流量，不在已存在故障时继续推进。

注意：`/health` 不证明数据库/Redis 或上游模型可用。合成 API/组件测试不能替代真实浏览器与真实模型验收。
